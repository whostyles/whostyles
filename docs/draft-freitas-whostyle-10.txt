                 The Whostyle Protocol (V1) Specification
                       draft-freitas-whostyle-10

Abstract

   This document defines Whostyle Protocol V1, a structured, data-driven 
   format for syndicating personal typographic and cosmetic styles 
   across decentralized web platforms (e.g., the IndieWeb, Fediverse).
   By constraining user-defined styles to a strict subset of design 
   tokens encoded via mathematical bitpacking into a 54-byte Base64 hash, 
   this specification enables host platforms to render third-party 
   syndicated content while guaranteeing layout integrity, performance, 
   accessibility, and mitigation of CSS injection vulnerabilities.

1.  Introduction

   Decentralized web interactions, such as Webmentions [W3C.REC-webmention],
   often strip the original author's visual identity when displaying 
   syndicated responses on a host platform. Prior attempts to preserve 
   visual identity relied on raw CSS injection or IFrames, 
   introducing severe security vectors and high computational overhead.

   Whostyle V1 solves these design flaws by abstracting cosmetic 
   styles into a mathematical bitpacked hash (e.g., {ws1:...}). 
   This format translates styling into non-executable design data, 
   eliminating structural layout properties (such as position, display, 
   and float) and third-party asset loading (such as external web fonts).

2.  Discovery Mechanism

   To apply a Whostyle identity, the author's platform MUST broadcast 
   the styling data Hash. This can be done at the protocol level (HTTP), 
   the document head (Meta, Link, JSON-LD), or the document body (Inline).

   Identifier Case-Insensitivity: Across all discovery mechanisms (HTTP 
   headers, HTML attributes, JSON keys, twtxt fields, and ActivityPub 
   properties), the identifier string "whostyle" (or "X-Whostyle") MUST 
   be treated as case-insensitive by parsers. The Base64 hash payload 
   itself, however, remains strictly case-sensitive.

2.1. Discovery Precedence

   To prevent malicious actors from injecting styles that override the 
   document author's legitimate configuration (e.g., via user-generated 
   comments), host engines MUST discover and extract hashes in the 
   following strict order of precedence:

   1. HTTP Response Headers (`X-Whostyle`)
   2. HTML `<meta>` tags
   3. JSON-LD scripts
   4. Inline Text (Fallback)

   If a valid `{ws1:...}` hash is found at a higher precedence level, 
   the parser MUST immediately stop searching and apply that hash.

2.2. HTTP Header Discovery (Level 1)

   The most secure method of syndicating a Whostyle hash is via the 
   `X-Whostyle` HTTP response header. Since headers are controlled 
   exclusively by the host server, they are immune to XSS and content 
   injection.

   Example:
   X-Whostyle: {ws1:tP3ClmkB9fXwGhouAFXM3d3dGhou9fXwZqr_MzNE}

2.3. Meta Tag Discovery (Level 2)

   If HTTP headers cannot be modified, authors SHOULD embed the payload 
   within the document's `<head>` using a meta tag.

   Example representation in HTML:
   <meta name="whostyle" content="{ws1:tP3ClmkB9fXwGhouAFXM3d3dGhou9fXwZqr_MzNE}">


2.4. JSON-LD Discovery (Level 3)

   Authors syndicating structured data MAY embed the hash as a top-level 
   attribute within a JSON-LD block.

   Example:
   <script type="application/ld+json">
   {
     "@context": "https://schema.org",
     "@type": "Article",
     "whostyle": "{ws1:tPXGAKCm9fXwGhouAFXM3d3dzMzMGhou9fXwZqr.MzNEVVVm}"
   }
   </script>

2.5. Inline Text Discovery (Level 4 - Fallback)

   If the author has no access to the `<head>` or HTTP headers (e.g., 
   posting a comment on a legacy platform), the hash MAY be placed 
   directly in the body text.
   
   Host engines MUST scan the raw text for the regex pattern: 
   \{ws1:[A-Za-z0-9\-.]{48}\}
   
   Inline Escape Sequence: If a backslash `\` precedes the hash (e.g., 
   `\{ws1:...}`), parsers MUST ignore it. This serves as an escape 
   sequence to allow citing hashes in prose without activating them.
   Normative parsing algorithm: Implementations MUST evaluate a standard 
   regex, and then programmatically check if the 
   character immediately preceding the match is a backslash (`\`). If it 
   is, the match MUST be skipped. Implementations MUST NOT use regex 
   lookbehinds (e.g., `(?<!\\)`) to implement this rule, as they are not 
   supported by engines such as RE2, Rust's `regex`, or Go's `regexp`.

   Hash Collisions: If a document contains multiple inline hashes, the 
   parser MUST extract and apply only the first unescaped inline hash 
   encountered.

2.6. ActivityPub Profile Discovery (Fediverse)

   To syndicate styles across federated networks (such as Mastodon, Misskey, 
   or Pleroma) without requiring modifications to the backend server software, 
   authors MAY place the Whostyle Hash in their ActivityPub profile metadata.
   
   Clients (e.g., alternative web interfaces, browser extensions, or mobile 
   apps) MUST inspect the author's PropertyValue attachments for a valid 
   {ws1:...} hash. If multiple `PropertyValue` attachments exist, the 
   parser MUST select the first one where the `name` field (case-insensitive) 
   equals `whostyle` or `Whostyle`.

2.7. twtxt Feed Discovery

   Authors publishing a twtxt feed [TWTXT] MAY broadcast their Whostyle
   hash using the Metadata extension [TWTXT-META]. The hash is embedded
   as a comment-based key-value field in the feed file header.

   Format:
   # whostyle = {ws1:CCCCCCCCxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx}

   The field name "whostyle" is case-insensitive, as required by the
   twtxt Metadata specification. Whitespace around the value MUST be
   stripped by the parser.

   Example twtxt feed header:
   # nick = user
   # url = https://example.com/twtxt.txt
   # avatar = https://example.com/avatar.png
   # whostyle = {ws1:tPXGAKCm9fXwGhouAFXM3d3dzMzMGhou9fXwZqr.MzNEVVVm}

   Note: twtxt feed discovery is a standalone extraction mechanism,
   independent of the HTML discovery precedence chain (Section 2.1). 
   Host engines consuming twtxt feeds SHOULD use a dedicated 
   extractFromTwtxt() method (or equivalent) rather than the HTML-based 
   discover() pipeline.

2.8. Hash Extraction and Cleaning

   Regardless of which hash is prioritized, the host engine SHOULD remove 
   all inline hashes from the presentation layer (the final HTML output) 
   during the cleaning phase to prevent them from being rendered to the 
   end user.

   To safely clean the presentation layer without inadvertently removing 
   hashes from within <meta> tags (both unescaped in the <head> and HTML-escaped 
   within code examples), implementations SHOULD use the following 
   replacement logic (or equivalent parser behavior).

   Note: DOM traversal (if available in the host environment) is the 
   safest and preferred method for discovering the meta tag. The following 
   Regex should be used as a fallback for contexts without a DOM parser.
   The 50,000 character limit recommendation (Section 6) applies equally 
   to this HTML cleanup regex.

   Regex Pattern:
   /((?:<|&lt;)meta[\s\S]{0,250}?name=(?:["']|&quot;|&#39;|&#039;)?whostyle(?:["']|&quot;|&#39;|&#039;)?[\s\S]{0,250}?content=(?:["']|&quot;|&#39;|&#039;)?\{ws1:[A-Za-z0-9\-.]{48}\}(?:["']|&quot;|&#39;|&#039;)?[\s\S]{0,250}?(?:>|&gt;))|(\{ws1:[A-Za-z0-9\-.]{48}\})/i

   Replacement Rule:
   If Group 1 matches, replace with Group 1 (preserve meta tag).
   If Group 2 matches, replace with an empty string (remove inline hash).

   Escaped Hashes: Parsers MUST search for the hash within the raw HTML 
   string before performing any entity unescaping. HTML-escaped hashes 
   (such as &#123;ws1:... or &lbrace;ws1:...) MUST NOT be extracted.
   When an escaped hash (e.g., `\{ws1:...}`) is encountered, the cleaning 
   process MUST remove the preceding backslash `\`, leaving the raw 
   `{ws1:...}` hash visible in the rendered output for the end user.

3.  Hash Specification

   A Whostyle Hash MUST consist of exactly 54 characters, formatted as:
   {ws1:AAAABBBBxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx}

   Where:
   - "{ws1:" (5 chars) is the protocol prefix.
   - "AAAA" (4 chars) is the Base64 representation of Configuration Group A.
   - "BBBB" (4 chars) is the Base64 representation of Configuration Group B.
   - "x" (40 chars) is the Base64 representation of the 10 Theme Colors.
   - "}" (1 char) is the suffix.

3.1. Base64 Alphabet

   The encoding MUST strictly use the following 64-character alphabet:
   ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-.

   Each character maps to its zero-indexed position in this string
   (A=0, B=1, ..., Z=25, a=26, ..., z=51, 0=52, ..., 9=61, -=62, .=63).
   The 48-character Base64 payload is strictly case-sensitive. The keys
   `whostyle` or `X-Whostyle` used in headers and tags are case-insensitive.

3.2. Version Extensibility

   The protocol prefix "{ws1:" explicitly identifies this specification 
   as Version 1. Future revisions of this protocol MUST use an incremented 
   version prefix (e.g., "{ws2:", "{ws3:"). Parsers encountering a hash 
   with an unrecognized version prefix MUST silently ignore it and MUST NOT 
   attempt partial decoding. This ensures forward compatibility and allows 
   future versions to change the internal encoding without breaking 
   existing deployments.

4.  Configuration Bitpacking (Radixes)

   To ensure safe decoding across all architectures, including constrained 
   32-bit systems, the Configuration state is split into two independent 
   integer blocks (Group A and Group B), each encoded into 4 Base64 
   characters. 

   The integer for each group is constructed by sequentially packing 
   properties using mixed-radix (variable-base) arithmetic, in the strict 
   order defined below. This order is normative and MUST NOT be altered.
   The encoding uses a little-endian byte order: the least significant 
   digit is stored first (leftmost character), and the most significant 
   digit is stored last (rightmost character).

4.1. Radix Definitions and Encoding Order

   Group A (Properties 0-6):
   Index   Property         Radix   Range   Description
   -----   --------         -----   -----   -----------
   0       typography       28      0-27    Font stack index (Appendix C)
   1       transform        4       0-3     Text transform (Appendix D.1)
   2       align            4       0-3     Text alignment (Appendix D.2)
   3       list             5       0-4     List style type (Appendix D.3)
   4       border_style     10      0-9     Border style (Appendix D.4)
   5       bg_texture       32      0-31    Background texture (Appendix D.5)
   6       border_width     17      0-16    Border width in px (direct)

   Group B (Properties 7-14):
   Index   Property         Radix   Range   Description
   -----   --------         -----   -----   -----------
   7       border_radius    17      0-16    Border radius in px (direct)
   8       shadow_offset    9       0-8     Shadow offset (see §4.2)
   9       shadow_blur      9       0-8     Shadow blur in px (direct)
   10      letter_spacing   26      0-25    Letter spacing (see §4.2)
   11      texture_opacity  4       0-3     Texture opacity (see §4.2)
   12      shadow_opacity   4       0-3     Shadow opacity (see §4.2)
   13      texture_size     4       0-3     Texture scale (see §4.2)
   14      checksum         6       0-5     Data integrity check (see §4.4)

   Encoding Pseudocode (pack):
   // Group A
   valueA = 0
   for key in [border_width, bg_texture, border_style, list, align, transform, typography]:
       valueA = valueA * RADIX[key] + config[key]
   for i in 0 to 3:
       outputA[i] = ALPHABET[valueA % 64]
       valueA = floor(valueA / 64)

   // Group B
   valueB = 0
   for key in [checksum, texture_size, shadow_opacity, texture_opacity, letter_spacing, shadow_blur, shadow_offset, border_radius]:
       valueB = valueB * RADIX[key] + config[key]
   for i in 0 to 3:
       outputB[i] = ALPHABET[valueB % 64]
       valueB = floor(valueB / 64)

   Decoding Pseudocode (unpack):
   // Group A (first 4 characters)
   valueA = 0
   multiplier = 1
   for i in 0 to 3:
       valueA = valueA + ALPHABET_INDEX[inputA[i]] * multiplier
       multiplier = multiplier * 64
   for key in [typography, transform, align, list, border_style, bg_texture, border_width]:
       config[key] = valueA % RADIX[key]
       valueA = floor(valueA / RADIX[key])
   if valueA != 0: reject("Group A invalid")

   // Group B (next 4 characters)
   valueB = 0
   multiplier = 1
   for i in 0 to 3:
       valueB = valueB + ALPHABET_INDEX[inputB[i]] * multiplier
       multiplier = multiplier * 64
   for key in [border_radius, shadow_offset, shadow_blur, letter_spacing, texture_opacity, shadow_opacity, texture_size, checksum]:
       config[key] = valueB % RADIX[key]
       valueB = floor(valueB / RADIX[key])
   if valueB != 0: reject("Group B invalid")

   The maximum integer state for Group A is 12,185,600 (24 bits) and for 
   Group B is 13,747,968 (24 bits). Both states comfortably fit inside 
   the 16,777,215 (24-bit) limit provided by their respective 4-character 
   Base64 blocks, preventing INT32 overflows in legacy software.

4.2. Numeric Property Conversion Formulas

   Some properties require a mathematical transformation to convert from 
   their encoded integer value to the final CSS value. The following 
   formulas are normative:

   Property          Formula              CSS Range
   --------          -------              ---------
   border_width      value + "px"         0px to 6px
   border_radius     value + "px"         0px to 16px
   shadow_offset     (value - 4) + "px"   -4px to 4px
   shadow_blur       value + "px"         0px to 8px
   letter_spacing    (value × 0.1 - 0.5)  -0.5px to 2.0px
                     + "px" (1 decimal)
   texture_opacity:
   0: 0.0, 1: 0.25, 2: 0.50, 3: 0.75
   Host CSS formula: `opacity: var(--ws-topacity);` (applied to texture pseudo-element)

   texture_size:
   0: 8px, 1: 16px, 2: 24px, 3: 36px
   Host CSS formula: `background-size: var(--ws-tsize) var(--ws-tsize);` (applied to textures that utilize scaling)

   Note on Shadow Offset: The shadow_offset value is applied to BOTH the 
   horizontal (X) and vertical (Y) offset of the CSS box-shadow property, 
   producing a diagonal shadow. This is by design to minimize the bit 
   cost while providing meaningful visual variety.

   Note on Texture Opacity: The alpha channel mapping allows authors to 
   soften the intensity of the structural patterns without breaking the 
   host's background colors.

4.3. Theme Color Encoding

   The final 32 Base64 characters encode exactly 8 Theme Colors in the 
   following strict order:
   
   1. Light Background
   2. Light Text
   3. Light Accent
   4. Light Texture (Color)
   5. Dark Background
   6. Dark Text
   7. Dark Accent
   8. Dark Texture (Color)

   *(The Texture Color defines the 24-bit RGB fill color applied to the 
   pattern selected by `bg_texture`)*

   Each color is represented as a 24-bit RGB hexadecimal value (e.g., #FFFFFF).
   Color encoding uses big-endian byte order (most significant bits first), 
   in contrast to the little-endian configuration encoding (Section 4.1). 
   To encode a color into 4 Base64 characters, the 24-bit RGB value is 
   treated as an integer, and sliced into four 6-bit segments using bitwise 
   operations. Each 6-bit segment acts as an index into the Base64 alphabet.

   Encoding Example (Pseudocode):
   val = parseInt(hex.replace('#', ''), 16);
   char1 = ALPHABET[(val >> 18) & 63];
   char2 = ALPHABET[(val >> 12) & 63];
   char3 = ALPHABET[(val >> 6) & 63];
   char4 = ALPHABET[val & 63];

   Decoding Example (Pseudocode):
   val = 0;
   val = (val << 6) | ALPHABET.indexOf(char1);
   val = (val << 6) | ALPHABET.indexOf(char2);
   val = (val << 6) | ALPHABET.indexOf(char3);
   val = (val << 6) | ALPHABET.indexOf(char4);
   hex = '#' + val.toString(16).padStart(6, '0');

   Invalid Colors & Contrast Thresholds: If the 32 characters decode to an 
   RGB value that theoretically passes mathematical contrast limits (e.g., 
   text #f5f5f5 on background #ffffff resulting in a 4.51:1 contrast) but 
   is subjectively illegible, the protocol's fallback is not triggered. 
   This is a known limitation of mathematical modeling, and host platforms 
   are encouraged to apply stricter mitigations as detailed in Section 6.

   *Note on Textures:* The `bg_texture` property acts as an integer 
   index (0-31) mapping to a predefined set of structural patterns 
   provided by the host engine (see Appendix D.5). It does not dictate 
   color; the texture color is defined by the Theme Colors above.

4.4. Data Integrity Checksum

   To prevent accidental configuration corruption (e.g., from truncated 
   copy-pasting or character replacement), the 12th property packed into 
   the configuration integer is a Checksum.
   
   The checksum is calculated on the sender's side before base64 encoding 
   Group B, using a weighted modulo-6 algorithm over all other 14 properties.

   Weights:
   typography=1, transform=2, align=3, list=4, border_style=5, 
   bg_texture=6, border_width=7, border_radius=8, shadow_offset=9, 
   shadow_blur=10, letter_spacing=11, texture_opacity=12, shadow_opacity=13,
   texture_size=14.
    
   Calculation Pseudocode:
   sum = 0
   for i = 0 to 12:
       sum = sum + (config[Properties[i]] * Weights[i])
   checksum = sum % 6
   
   Parsers MUST recalculate this checksum after decoding the configuration 
   properties. If the computed checksum does not match the decoded 
   checksum property, the entire payload MUST be discarded as corrupted, 
   returning a null or error state.

5.  Processing and Host Enforcement Rules

5.1.  Strict Structural Omission

   Host implementations MUST NOT parse, translate, or inject structural layout 
   properties from the syndicated entity. Properties including, but not 
   limited to, "position", "display", "float", "clear", "width", "height", 
   "z-index", "margin", and "padding" are explicitly forbidden to ensure the 
   host platform retains absolute authority over document geometry.

5.2. Minimum Contrast Validation (WCAG)

   Host engines MUST compute the relative luminance contrast ratio between 
   the background color and all foreground colors (text, accent/links).
   For texture contrast, the host engine MUST compute the effective 
   blended color of the texture overlaid on the background color, using 
   standard alpha compositing based on the decoded `texture_opacity`. 

   The contrast ratio MUST be evaluated against this effective blended 
   color. If any of the following checks yield a ratio lower than 4.5:1, 
   the host engine MUST reject the entire color scheme for that mode (Light 
   or Dark) and fallback to its safe defaults.

   Checks performed:
   - Text vs Background
   - Accent vs Background
   - Text vs Effective Texture Color
   - Accent vs Effective Texture Color

   If the computed contrast ratio is less than 4.5:1, the host engine MUST 
   override the colors to ensure legibility. In the event of a contrast 
   failure, ALL colors for that specific mode (light or dark) MUST revert to 
   the following safe default standard:
   
   - Light Mode: Background #ffffff, Text #000000, Accent #0000ff, 
                 Texture Color transparent, Border #cccccc
   - Dark Mode: Background #000000, Text #ffffff, Accent #00aaff, 
                Texture Color transparent, Border #555555

6.  Security Considerations

   Whostyle V1 addresses major security concerns associated with arbitrary 
   CSS ingestion. By avoiding raw stylesheet parsing, libraries are 
   immune to CSS-based data exfiltration and blind injection attacks. 
   The fixed 54-byte hash prevents bandwidth exhaustion.

   Regular Expression Denial of Service (ReDoS): Host engines must take 
   extreme care when parsing large, unbounded user-generated text for 
   inline hashes (as defined in Section 2.5). Implementations MUST enforce 
   the following protections:
   
   1. Maximum Length Bounding: The regex MUST NOT be run on strings 
      exceeding 50,000 characters. For larger documents, parsers MUST 
      only scan a truncated subset or rely entirely on Meta/Header tags.
   2. Engine Selection: Implementations SHOULD utilize linear-time (O(N)) 
      regex engines (e.g., RE2, Rust's `regex` crate, or Go's `regexp`) 
      to prevent catastrophic backtracking.
   3. Fallback Complexity Limits: If linear-time engines are unavailable 
      (e.g., native JavaScript or PHP PCRE without strict limits), 
      implementations MUST strictly bound quantifiers inside lookarounds 
      and non-capturing groups, and SHOULD limit the regex execution time 
      (e.g., using `pcre.backtrack_limit` in PHP).

   Contrast Poisoning: The protocol enforces a baseline WCAG AA contrast 
   ratio of 4.5:1 (Section 5.2). However, a malicious actor could 
   intentionally generate a color scheme that barely passes this 
   threshold (e.g., 4.51:1) to degrade the legibility of the host 
   platform. Because mathematical thresholds cannot perfectly account for 
   all visual impairments, host platforms MAY enforce stricter requirements 
   (such as WCAG AAA 7:1) or provide user-level accessibility toggles 
   to forcibly override syndicated colors.
